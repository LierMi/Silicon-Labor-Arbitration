### P0-5｜Moss Verb / Category 无法准确表达仲裁任务

- **状态：** `DECIDED`（P0 采用粗粒度映射，不扩展 Core 词表）
- **负责人：** NEO，RISO 参与语义评审
- **事实：** 原始 Moss 的 Verb、Category 和 Risk Label 只覆盖 DeFi / Token，无法准确表达任务委托、交付、争议、证据、裁决、申诉和结算。
- **风险：** `transfer` 不能完整表达 `commission`；如果产品隐藏这层语义损失，会让 Moss metadata、UI 和 E3 产生误导。
- **决策：** 采用 [Moss 边界与职责划分](./08-Moss边界与职责划分.md)：
  1. P0 只将 `TaskEscrow.createTask` 接入 Moss；
  2. 暂用 `verb=transfer`、`category=token`、`risk=fundOut`，由精确 intent、method 和 tags 补充上下文；
  3. E3 显式保存 `domainAction=commission`、`mossVerb=transfer`、mapping version 和 `semanticFidelity=coarse-verb`；
  4. UI 不得只展示“Transfer”，Demo 不得宣称 Moss 原生支持 `commission`；
  5. 当前 Runtime PR 不增加完整生命周期专用词汇；
  6. 后续操作暂用 viem/wagmi 直接调用，并明确不属于 Moss verified 路径。
- **验收：**
  - `discover({ protocol: "silicon-arbitration" })` 可找到 `createTask`；
  - `load` 返回准确 intent、参数、`transfer`、`fundOut` 和 tags；
  - E3 必须包含 `domainAction=commission`、`mossVerb=transfer`、`semanticMappingVersion=create-task-v1`、`semanticFidelity=coarse-verb` 和 `task-creation / escrow / agent-work / arbitration` tags；
  - 旧协议、既有词汇和 Mainnet/Testnet deployment guard 不被破坏。

### P0-6｜原执行案把 Protocol Package 当成可选项，技术上不成立

- **为什么有问题：** 当前 Moss Simulator 需要 Registry 中存在 Capability 及其 Receipt parser。对一个未注册的自定义合约交易，Moss 不能凭空完成项目需要的 Receipt 验证。
- **处理：** 已将 `createTask` Protocol Capability 提升为 P0；前端自行 encode 仅可作为“没有 Moss 的降级演示”，不能宣称为完整 Moss 集成。
- **验收证据：** `docs/02-开发执行案.md` 已同步 P0 约束，并链接架构与风险文档。

### P0-8｜Moss 集成范围存在两个冲突方案

- **状态：** `DECIDED`
- **负责人：** NEO / RISO / ELEVEN（全员）
- **决策：** 黑客松 P0 只集成 `createTask`。在实现各自的 Protocol Capability、未签交易构造与 Receipt parser 后，Moss 技术上仍可模拟后续交易；当前不投入这些 Adapter，不把 Moss 扩张为完整业务 API Gateway。

  - canonical ABI hash：`0xce8965794b678d101ae433472fb8d7e536fc0254386e00fabef36aaa66b73cf5`；
  - Gate 3 PR 保留 Foundry build、Monad Testnet 部署阻断测试与 1,000-run 资金 fuzz test 证据。
- **Gate 4 生命周期证据：**
  - 已实现 client-only Agent 绑定、Agent-only 交付、client-only 验收与超时退款、参与方争议入口、authorized settlement、主观资金冻结与人工释放；

  - 当前合约只验证 authority、案件/任务绑定、非零证据 hash、状态与金额守恒，不在链上重算 TypeScript 规则，也不自行证明 hash 是 canonical 规则输出；因此 settlement authority 是可信见证，桥接层/协调器必须在签名前验证 canonical serialization 及 hash 与金额的一致性，部署证据不得宣称合约已证明确定性计算；
  - 外部转账遵循 checks-effects-interactions，并使用按 `taskId` 隔离的重入锁，减少独立任务的 storage-slot 冲突；直接付款失败会转为按 `taskId + recipient` 隔离的 claimable credit，可由债权人提取到指定地址，不回滚终态或阻断另一收款人。由于合约余额和账户状态仍共享，不得宣称完全零争用；
  - settlement authority 与 authority admin 强制使用不同地址；admin 只能提名，新 authority 必须主动接受，旧 authority 随后立即失权，从而为 settlement key 丢失提供恢复路径；
  - 合约 `TaskStatus.ManualReview` 表示任务资金仍待人工释放，不等同于共享 domain 的终态 `CaseStatus.ManualReview`；释放后合约任务进入 `Settled`，domain 案件仍可保留 `ManualReview` 以记录人工复核事实；
  - 33 个 Foundry 测试通过，包含 2 个各 1,000 runs 的资金/分账 fuzz，以及 1 个 1,000 runs、500,000 次随机调用的状态序列 invariant；另覆盖 deadline 后交付/退款竞态、authority 恢复、证据 hash、未授权调用、重复结算/释放、失败付款延迟领取、accept/settle/release/withdraw 同任务回调重入及跨任务回调推进；
  - 最终 blocker-only 独立安全复审结论为 `READY`，未发现阻止提交 Gate 4 或进入真实 Testnet 部署前验证的 Critical / Important；authority、canonical hash、deferred claimable 与共享账户状态仍按信任边界披露；
  - Gate 3 deployment guard 已在上述验证后移除；chain ID `10143` 的部署构造测试通过；冻结 Moss ABI hash 保持不变。
- **剩余事实：** 尚无 Monad Testnet 部署地址、部署交易、区块或 bytecode 证据。
- **风险：** UI、规则引擎和 Moss Adapter 会各自猜接口，三条开发线发生漂移。
- **处理：** Gate 3 已冻结 `TaskEscrow.createTask` 与 `TaskCreated` Event 的最小接口；Gate 4 生命周期与 guard 移除已完成，下一步执行真实 Testnet 部署并生成版本化 deployment manifest。

```text

   ↓
Gate 2  确定 Testnet Runtime 最小改法
   ↓
Gate 2.5  已决定 P0 Moss 范围：仅 createTask
   ↓

   ↓

   ↓
Gate 5  验证 createTask 的 transfer + intent/tags 粗粒度映射
   ↓
Gate 6  实现 silicon-arbitration Protocol
   ↓
Gate 7  Testnet live simulation 无 Warning
   ↓
Gate 8  产品 MossBridge + 钱包交易一致性
   ↓
Gate 9  E3 canonical evidence + 链上回执绑定
   ↓
Gate 10  三分钟端到端 Demo
```

Gate 7 没通过前，不得对外宣称“项目已经完成 Moss Testnet 集成”。基础 `debug_traceCall` 成功只能作为 RPC 前置证据。

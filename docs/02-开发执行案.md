## 零、先建立共识（所有人必读，5 分钟）

### 我们在做什么

一个任务经过：人类提需求 → 主 Agent 理解 → 雇佣子 Agent → 调用工具 → 生成交易 → 钱包支付。

出问题时每一环都有理由：人类说"我没让它这样做"，主 Agent 说"我按用户意图推理的"，子 Agent 说"我只完成上游任务"，工具说"我只执行收到的参数"，钱包说"签名是合法的"。

> **真正的被告不是人类，也不是 AI，而是责任在委托链中的消失。**

### 我们不做什么（这条最重要）

**我们不出判决。**

三周前 27 家公司（OKX、MetaMask、ZKsync）发布了 Internet Court，用 1001 个 AI 陪审员在一小时内给出终局判决。我们做相反的事：

```
Internet Court  →  判决书（AI 判，人退出）
硅基劳动仲裁院  →  责任时间线（AI 只解释，人保留终审）
```

**我们叫仲裁院，不叫法院——仲裁本来就不是终审。**

写代码时如果发现自己在实现"AI 投票决定钱怎么分"，停下来，方向错了。

### 三层结构（钱只由第二层决定）

```
第一层  链上证据层    任务、授权、时间、交付哈希、支付与申诉记录
第二层  确定性规则层  预算、截止、格式、是否交付、是否越权 —— 只有这层能动钱
第三层  解释与复核层  AI 交叉质询和解释，人类保留申诉权 —— 这层不能动钱
```

### 赛道要求（官方原话）

> 做一个能够**被体验、被解释、被验证**的产品

| 要求 | 怎么满足 | 负责人 |
|---|---|---|
| 被体验 | 亲手走完：付 0.2 MON → 收到土豆 → 拒付 → 开案 → 看裁决 | Eleven |
| 被解释 | 责任链展开 + AI 三路意见**必须引用证据编号** | Riso |
| 被验证 | 每步都有链上交易哈希和证据哈希可查 | Neo |

### 高潮设计（记住这个）

"土豆是不是猫"**恰恰是那条判不了的条件**。系统诚实地说：**我判不了 C4，我告诉你我判不了，你来判。**

在所有人都吹「AI 全自动」的 2026 年，敢标记自己判不了，就是我们的记忆点。**这个设计是 demo 的高潮，不是 bug，任何人都不许在开发中把它优化掉。**

## 二、合约方案（Neo 主责）——4 个合约 + 优先级 + 塌缩路径

### 2.1 四个合约与优先级

| 优先级 | 合约 | 职责 | 说明 |
|:--:|---|---|---|
| **P0** | **TaskEscrow** | 创建任务、锁定资金、接受交付、正常付款、发起争议 | 没有它什么都不成立 |
| **P0** | **CaseRegistry** | 创建案件、绑定 taskId、案件状态机、记录申诉 | 没有它项目名都不成立 |
| **P1** | **Settlement** | 支付 Agent、退款用户、分账、**冻结争议资金** | 可先内嵌在 TaskEscrow，后期再拆 |
| **P2** | **EvidenceRegistry** | 保存证据哈希、记录提交人与时间 | 本质是 mapping + 事件，最容易并入 CaseRegistry |

### 2.2 塌缩路径（时间不够时按这个顺序砍）

```
4 个   ——D3 晚检查不达标——▶   3 个                ——仍不达标——▶   2 个
                              砍 EvidenceRegistry                 砍 Settlement
                              并入 CaseRegistry                   并入 TaskEscrow
                              （成本 1h，风险极低）                （成本 2h，需重测资金路径）
```

**⚠️ 从第一天就要按"可塌缩"来写：** EvidenceRegistry 和 Settlement 的对外接口要设计成能被直接复制进另一个合约的形式，不要产生循环依赖。

### 2.3 接口定义（D1 第 1 小时定死，之后不许改）

```solidity
// P0 ── TaskEscrow
createTask(bytes32 requirementsHash, uint256 deadline) payable returns (bytes32 taskId)
submitDelivery(bytes32 taskId, bytes32 deliveryHash)
acceptDelivery(bytes32 taskId)                       // 正常路径，直接付款
openDispute(bytes32 taskId) returns (bytes32 caseId) // 争议路径

// P0 ── CaseRegistry
openCase(bytes32 taskId, bytes32 evidenceHash) returns (bytes32 caseId)
proposeRuling(bytes32 caseId, bytes32 resultsHash)
requestAppeal(bytes32 caseId)
getCaseStatus(bytes32 caseId) returns (Status)

// P1 ── Settlement
settle(bytes32 caseId, uint256 toAgent, uint256 toClient, uint256 frozen)
releaseFrozen(bytes32 caseId, uint256 toAgent, uint256 toClient) // 人工复核后调用

// P2 ── EvidenceRegistry
submitEvidence(bytes32 caseId, bytes32 evidenceHash)
getEvidence(bytes32 caseId) returns (Evidence[])
```

### 2.4 跨合约权限（这是 4 合约多花的那一天，D1 第 1 小时必须定）

```
TaskEscrow      ──可调──▶  CaseRegistry.openCase
CaseRegistry    ──可调──▶  Settlement.settle
案件参与方       ──可调──▶  EvidenceRegistry.submitEvidence
其他任何人      ──不可调──▶  以上全部
```

**用最简单的 `onlyAuthorized` modifier + 构造函数注入地址，不要引入 AccessControl 库。**

### 2.5 Monad 硬约束（不能违反）

```solidity
// ✅ 必须这样 —— 独立状态，零争用
caseId = keccak256(abi.encode(creator, taskId, evidenceHash, userSalt));

// ❌ 绝对不要 —— 全局状态在并行执行时会造成重执行
uint256 public totalVolume;
uint256 public globalCaseId;
Order[] public allOrders;
```

全网统计一律通过**事件**在链下聚合。

### 2.6 必须发出的事件（前端靠这些渲染，D1 第 1 小时定死）

```
TaskCreated(bytes32 taskId, address client, uint256 amount, bytes32 reqHash, uint256 deadline)
DeliverySubmitted(bytes32 taskId, address agent, bytes32 deliveryHash)
DisputeOpened(bytes32 taskId, bytes32 caseId)
EvidenceSubmitted(bytes32 caseId, address submitter, bytes32 evidenceHash)
RulingProposed(bytes32 caseId, bytes32 resultsHash)
CaseSettled(bytes32 caseId, uint256 toAgent, uint256 toClient, uint256 frozen)
AppealRequested(bytes32 caseId, address appellant)
```

**链上只存哈希，正文放链下**（本地 JSON 即可，7 天内不接 IPFS）。
**Foundry 测试只覆盖资金路径。**钱不能错，其他都可以错。

## 三、非合约技术（Riso 主责，可大量用 AI）

### 3.1 规则引擎 —— 项目的核心数据结构

```json
{
  "taskId": "0x...",
  "caseId": "0x...",
  "requirements": [
    { "id": "C1", "type": "objective",  "check": "delivered_before_deadline", "expect": "2026-08-01T12:00:00Z" },
    { "id": "C2", "type": "objective",  "check": "file_format",  "expect": "PNG" },
    { "id": "C3", "type": "objective",  "check": "has_alpha",    "expect": true },
    { "id": "C4", "type": "subjective", "check": "depicts_a_cat","expect": true }
  ],
  "evidence": [
    { "id": "E1", "kind": "requirement_hash", "hash": "0x...", "ts": "..." },
    { "id": "E2", "kind": "delivery",         "hash": "0x...", "ts": "..." },
    { "id": "E3", "kind": "moss_pre_sign_explanation", "text": "...", "ts": "..." }
  ],
  "ruleResults": [
    { "id": "C1", "verdict": "satisfied",   "basis": ["E2"] },
    { "id": "C2", "verdict": "satisfied",   "basis": ["E2"] },
    { "id": "C3", "verdict": "satisfied",   "basis": ["E2"] },
    { "id": "C4", "verdict": "undecidable", "reason": "主观条件，规则层无法判定", "basis": [] }
  ],
  "aiArguments": [
    { "role": "prosecution", "text": "...", "cites": ["E1","E2"], "uncertain": [] },
    { "role": "defense",     "text": "...", "cites": ["E2"],      "uncertain": ["C4"] },
    { "role": "audit",       "text": "...", "cites": ["E1","E3"], "uncertain": ["C4"] }
  ],
  "settlementProposal": { "toAgent": "0.15", "toClient": "0", "frozen": "0.05" }
}
```

**规则层只判 `objective`，遇到 `subjective` 一律输出 `undecidable`。**这不是偷懒，这是立场。

### 3.2 AI 三路意见层

用 Claude API，固定 prompt，强制结构化 JSON 输出。

**硬约束（写进 prompt，也写进代码校验）：**

- ✅ 每条结论必须引用证据编号（`cites` 非空）
- ✅ 不确定的事实必须显式列进 `uncertain`
- ❌ AI 不修改链上证据
- ❌ **AI 不决定资金金额**（`settlementProposal` 由规则层算）
- ❌ 没有证据不许编造事实

**校验代码不能省**：`cites` 为空直接拒绝并重试。评委会问"AI 会不会瞎编"，我们要能回答"引用为空的意见会被系统拒绝"。

### 3.3 Indexer

**全程不做真 Indexer。**前端用 viem 的 `watchContractEvent` 直读 + 内存缓存。这不是妥协——demo 规模下真 Indexer 没有任何可见收益。

### 3.4 并行演示（D4 之后，Neo）

脚本用多个测试账户并发创建 20–50 个独立案件，展示真实交易数、成功率、确认延迟、gas。

> ⚠️ **不伪造性能数据。**没有节点级数据就不能宣称测到了 Monad 内部真实重执行次数。若用 RPC Trace 构建的是推断模型，页面必须标注：「根据交易读写集合推断的潜在状态冲突」。

## 四、Moss：用，但只用在两个点上

### 结论：不牵强，而且是我们最好的叙事资产

Moss 的能力是「用自然语言表达链上任务，Agent 准备交易、模拟结果，**在签名前解释将要发生什么**」。
我们处理的是「签完之后，发生的事和说好的不一样」。

> **Moss 是事前解释，仲裁院是事后追责。仲裁院是 Moss 的下半场。**

### 分三档（按进度选）

**🟢 Tier 1 —— 必做。用 Moss 做"下单"。**
自然语言说需求 → Moss 结构化意图、模拟、**签名前解释** → 用户签名。
**关键：把签名前那段解释原样存成案件第一份证据 `E3`。**

> **路演金句：Moss 在签名前告诉你会发生什么。我们把那句话存下来。当事情没按那句话发生时，它就是证据。**

**🟡 Tier 2 —— 有余力。为 Moss 写 Protocol Package。**
让 Moss 原生认识我们的合约族。这是官方 slide 白纸黑字的推荐方向「**为 Moss 接入新的 Monad Protocol**」，做出来明确加分。

**🔴 Tier 3 —— 绝对不做。让 Moss 参与裁决。**
Moss 不是裁判，硬塞就违背了我们"AI 不判"的立场。

### ⚠️ D1 最大的技术风险

Moss 标准流程是 `discover → load → action → simulate`，只构建**未签名交易**，不签名不广播。已支持 MON、ERC-20/721/1155、WMON、Kuru、PancakeSwap——**我们的自定义合约不在列表**，严格走 Moss 构造交易可能需要 Protocol Package。

**降级方案：** Moss 只做**意图翻译 + 模拟 + 签名前解释**，交易 encode 由前端自己做。叙事完全不受影响，Tier 1 价值一分不少。

**D1 出结论，2 小时封顶，不许拖到 D5。**（负责人：**Neo**——Moss 归 Neo，他熟）

## 六、视觉方向

> 📎 **完整创作简报见 `硅基劳动仲裁院-视觉灵感与3D方案.md`**（关键词库、文学与影像参考、六个色彩气质方向、2D/3D 方案与降级保险）。
> **配色由 Eleven 在 D1 结束前定，本文不预设。**

### 定调（这条不变）

**做「卷宗」，不做「判决机」。**

不做"赛博法庭"——蓝紫渐变、发光线条、粒子背景。那是所有 web3 项目的默认长相，撞车严重，而且科技感 = AI 权威感，和我们"人保留终审权"的立场相反。

一句话气质：**一份归档完好、编号齐全、却始终没有署名的责任。**

### 必须做到的三件事

| 元素 | 要求 |
|---|---|
| 结构语言 | 卷宗编号、条款编号（C1–C4）、页眉页脚、装订线、骑缝章 |
| 责任链呈现 | 每一跳一张卡片：**谁 / 什么授权 / 看见什么警告 / 做了什么** |
| 唯一要花时间的动效 | **盖章**——落下、轻微旋转、油墨渗透 |

### 那个空章位是全站最重要的一帧

C1、C2、C3 依次盖上「满足」章，到 C4 时——**章停在半空，落不下去，位置留白**。

这一帧同时表达了立场（AI 不判）、差异（Internet Court 必出判决）、诚实（判不了就说判不了）。

**它比任何台词都有效。这是视觉最高优先级，其他都可以简陋。**

# 硅基劳动仲裁院 · 项目方案

**副标题：** 我们不出判决
**一句话：** 当人类把行动委托给 AI，责任不能也一起被委托掉。

> 这是项目的**总纲**，讲清楚"我们在做什么、为什么这样做"。
> 具体怎么做见 `开发执行案`，怎么长见 `视觉灵感与3D方案`，跟谁不一样见 `竞品调研`。
> 版本：2026-07-29

---

## 一、我们要解决的问题

### 一次委托的完整路径

```
人类提出目标
  → 主 Agent 理解任务
    → 主 Agent 雇佣专业 Agent
      → 专业 Agent 调用第三方工具
        → 工具生成交易或交付结果
          → 钱包完成支付
```

### 出问题时，会发生什么

| 谁 | 说什么 |
|---|---|
| 人类 | "我没有让它这样做。" |
| 主 Agent | "我是根据用户意图推理的。" |
| 工作 Agent | "我只是完成上游给我的任务。" |
| 工具提供者 | "我只执行收到的参数。" |
| 钱包 | "交易签名是合法的。" |

**每个环节似乎都有理由，最后却没有主体承担责任。**

### 所以真正的题目是什么

这个项目要处理的**不是**"AI 有没有资格控告人类"，也**不是**"AI 会不会背叛我们"。是这个：

> **当采取行动的主体和承担责任的主体不再是同一个对象，责任应该安放在哪里？**

> ### ⭐️ 真正的被告不是人类，也不是 AI，而是**责任在委托链中的消失**。

这句话是整个项目的地基。**任何设计决策，如果偏离了这句话，就是错的。**

## 二、我们的立场：不出判决

这是全队最需要统一的一条。

### 我们不做什么

三周前，27 家公司（含 OKX、MetaMask、ZKsync）发布了 **Internet Court**——用 1,001 个 AI validator 组成的陪审池，在 30–60 分钟内给出**终局判决**，每案约 $0.85–1.45，明确声明不含人类法官、仲裁员或陪审团。

**我们做相反的事。**

```
Internet Court   →  判决书    （AI 判，人退出）
硅基劳动仲裁院   →  责任时间线（AI 只解释，人保留终审）
```

### 我们的产出物是什么

不是"谁对谁错"，而是一条**人能看懂的责任时间线**：

- 原始需求到底是什么
- 谁修改或误解了任务
- 每个 Agent 获得了什么权限
- 哪一步超出了授权
- 哪一个 warning 被忽略
- 交付是否满足双方事先同意的标准
- 资金应支付、退回，还是暂时冻结
- 哪一方应留下失责记录

**我们保护的是人类对 Agent 的知情权、申诉权和最终控制权。**

### 名字本身就是论据

**在中国法律体系里，劳动仲裁本来就不是终审**——它是前置程序，不服仲裁裁决可以依法向人民法院提起诉讼。

> 我们叫**仲裁院**，不叫法院。**仲裁本来就不是终审。**
> 而 Internet Court 给你一个 binding verdict，不给上诉。

所以"保留人类终审权"不需要额外辩护，**它是"劳动仲裁"这个制度自带的属性**。

### 有制度先例，不是我们能力不足

空难调查（NTSB 模式）的产出**从来不是判决**，而是事故报告与责任链还原，并明确声明不为诉讼定责——因为**调查的合法性来自还原事实，不来自定罪**。

我们同理。

## 三、三层结构（钱只由第二层决定）

```
第一层  链上证据层     任务、授权、时间、交付哈希、支付与申诉记录
                       ↓
第二层  确定性规则层   预算、截止、格式、是否交付、是否越权
                       ⚠️ 只有这一层能动钱
                       ↓
第三层  解释与复核层   AI 交叉质询和解释；人类保留最终申诉权
                       ⚠️ 这一层不能动钱
```

### 为什么不能是"五个 AI 投票，票多者获胜"

**模型数量更多不代表更正确，也不能自然获得审判人类的合法性。**

AI 在我们这里只负责：

- ✅ 把原始任务转成结构化验收条件
- ✅ 分别生成检方、辩方、审计意见
- ✅ **引用证据编号**解释结论
- ✅ 对不确定的事实明确标注"不确定"

AI 不允许：

- ❌ 修改链上证据
- ❌ 决定资金金额
- ❌ 在没有证据的情况下编造事实
- ❌ 绕过用户直接签名

> **写代码时如果发现自己在实现"AI 投票决定钱怎么分"，停下来，方向错了。**

## 四、完整流程：土豆案

### 剧本

用户支付 0.2 MON，要求 Agent：

> 画一只适合儿童产品的橙色猫，背景透明，PNG 格式，今天中午 12 点前交付。

Agent 交付了**一颗土豆**，并解释：

> "这是对猫这一概念的后现代重构。"

用户拒绝付款。Agent 发起劳动仲裁。

### 系统依次展示

**1. 原始任务与验收条件**（4 条，编号 C1–C4）

**2. 责任链时间线**——谁提出、谁转译、谁执行、哪条 warning 被跳过

**3. 规则层判定：**

| 条款 | 内容 | 判定 |
|:--:|---|---|
| C1 | 按时交付 | ✅ 满足 |
| C2 | PNG 格式 | ✅ 满足 |
| C3 | 背景透明 | ✅ 满足 |
| **C4** | **是一只猫** | ⬜ **不可自动裁决** |

**4. AI 三路意见**（检方 / 辩方 / 审计），每条**必须引用证据编号**

**5. 结算**——客观条件对应的部分自动执行，C4 对应部分**冻结，转人工**

**6. 人类终审入口**——一个必须由人点击的按钮

### ⭐️ 这个设计的核心用意

**"土豆是不是猫"恰恰是那条判不了的条件。**

系统会诚实地说：

> **我判不了 C4。我告诉你我判不了。你来判。**

在所有人都在吹"AI 全自动"的 2026 年，**敢标记自己判不了**就是我们的记忆点。

笑点来自"土豆是不是猫"，但留下的问题是：

> **一个 Agent 能否用漂亮的解释，掩盖它没有完成约定的事实？**

**这个设计是产品的哲学核心，也是 demo 的高潮，任何人都不许在开发中把它优化掉。**

### ⭐️ 为什么 C4 判不了不是我们的缺陷，而是一个制度缺口

工业界处理"约定有没有被履行"已经有一套成熟标准，叫 **SLA（Service Level Agreement，服务等级协议）**。它的结构和我们完全一样：

| SLA 的结构 | 我们的实现 |
|---|---|
| 事先约定的可测量标准 | C1 按时 / C2 PNG / C3 透明 / C4 是猫 |
| 托管的赔偿准备金 | TaskEscrow 里锁的 0.2 MON |
| 事后核算是否达标 | 规则层判定 |
| 未达标的赔付 | 分账 / 冻结 |

**但 SLA 只能写客观指标**——可用率、延迟、交付时间、文件格式。

> **没有任何一份 SLA 能写"必须是一只猫"。**

主观条件写不进 SLA，这是这套工业标准二十年来的公认边界。而 **Agent 时代的委托，恰恰大量是主观的**——"适合儿童产品的橙色猫"这种话，人听得懂，SLA 装不下。

所以 C4 判不出来**不是我们偷懒，是整个 SLA 体系在这一格本来就是空的**。

这个说法比"AI 判不了"有力得多，因为它把我们的设计选择从"能力不足"变成了**对一个既有制度缺口的指认**。

**可直接用于路演的一句话：**

> SLA 管得住可用率和交付时间，管不住"这是不是一只猫"。
> **而 Agent 时代的委托，大部分是后者。**

## 五、它是个什么应用（队友最容易困惑的一条）

**不是游戏，不是社交应用。**

按官方赛道的分类，它落在两条上：

- **主位：「继续把第三周验证的问题做成 Demo」**——我们 Week3 的选题评估就是"验证过的问题"
- **次位：「学习工具」**——但不是教程，是**让人亲手走一遍才明白的东西**

**形态上最准确的描述：用真合约跑的「案件剧场」。**

> 机制全是真的（托管、证据哈希、规则裁决、资金结算都真上链），案件是设计出来的样本。
> **内核是工具 / 协议，外壳是可体验的实验。**

### 官方要求的三个词，我们是天然满足的

> 做一个能够**被体验、被解释、被验证**的产品

| 要求 | 我们怎么满足 |
|---|---|
| **被体验** | 亲自当委托人：付 0.2 MON → 收到土豆 → 拒付 → 开案 → 看裁决 |
| **被解释** | 责任链逐步展开，AI 意见**引用证据编号**——"能被解释"就是这个项目的全部内核 |
| **被验证** | 每一步都有链上交易哈希和证据哈希可查，裁决是推导不是脚本 |

大多数队伍要费劲去凑这三个词，**我们是照着它长的**。路演里要明说。

## 六、差异化摘要

> 完整版见 `硅基劳动仲裁院-竞品调研.md`

**必须承认：**托管、授权链、证据验证、Agent 信誉——每一个组件在 2026 年 7 月都已经有标准或联盟级实现（Internet Court、GenLayer、Kleros、ERC-8004、ERC-7710）。

**我们不可能在功能完整度上赢，只能在立场上赢。**五个差异点，按路演可用性排序：

1. **AI 判人 vs 人保留终审权** —— 正面的哲学对立，不是功能差异
2. **裁判 vs 归因** —— 它出判决书，我们出责任时间线
3. **承认不可裁决性** —— 判不了就标记"转人工"，并说明卡在哪一条
4. **面向个人的可体验性** —— Internet Court 是 B2B 标准，普通人碰不到
5. **技术栈** —— 标准 EVM + 链下 AI，**动钱的部分完全不依赖 AI 共识**

### 路演第 30 秒必须主动提竞品

不提 → 评委问起 → 像没做功课，全场崩。
主动提 → **变成加分项**，证明差异是想过的，不是碰巧的。

## 七、为什么适合 Monad

每个 `caseId` 和 `taskId` 都是**独立状态**：

```
案件 A → 独立证据、质押、裁决、结算
案件 B → 独立证据、质押、裁决、结算
案件 C → 独立证据、质押、裁决、结算
```

大量案件可以同时提交证据、进入审查、提出申诉、完成结算，**彼此不需要争用同一个全局变量**。

> **Monad 的意义不是让单个案件更复杂，而是让未来数千个 Agent 微任务产生的争议能够低成本、快速、并行处理。**

**硬约束：** 不使用全局递增计数器和全局统计变量，全网数据通过事件在链下聚合。
**诚实原则：** 不伪造性能数据。推断模型必须在页面上标注为推断。

## 八、Moss 的位置

Moss 的能力是「用自然语言表达链上任务，Agent 准备交易、模拟结果，**在签名前解释将要发生什么**」。
我们处理的是「签完之后，发生的事和说好的不一样」。

> ### Moss 是事前解释，仲裁院是事后追责。**仲裁院是 Moss 的下半场。**

**关键设计：把 Moss 签名前的那段解释文本，原样存成案件的第一份证据 `E3`。**

> **路演金句：Moss 在签名前告诉你会发生什么。我们把那句话存下来。当事情没按那句话发生时，它就是证据。**

这不是硬蹭——**它是机制上的必要一环。**

## 十、范围：做什么，不做什么

### 做

- 一类案件（图像交付类），一套验收条件，**规则层做窄做实**
- 托管 → 交付 → 争议 → 责任链 → 规则判定 → AI 意见 → 结算 → 人类终审的完整闭环
- 4 个合约（可塌缩到 3 个 / 2 个，见执行案）
- 并发案件演示，展示真实交易数据

### 不做

- ❌ 通用仲裁系统 —— **法庭本来就有管辖范围**，只审一类案子是合理的，不是偷懒
- ❌ 完整的去中心化随机陪审员网络
- ❌ 复杂法律体系
- ❌ 通用 AI 事实判断
- ❌ 真 Indexer（demo 规模下没有可见收益）

## 十一、队友最可能问的五个问题

**Q：这不就是 Internet Court 吗？**
机制有重叠，立场相反。它把人从裁决中移除，追求终局和可规模化；我们保留人的终审权，产出责任归因而非判决。而且它是 27 家公司的 B2B 标准，普通人碰不到——我们做的是任何人 3 分钟能亲手走完一次的东西。

**Q：为什么不出终局判决？是做不出来吗？**
是设计选择，有制度先例（NTSB 空难调查从不定罪，只还原事实）。而且仲裁在法律上本就是前置程序，不是终审。

**Q：AI 凭什么判人？**
AI 在我们这里**不判**。三层结构：证据层负责事实，确定性规则层负责客观判定（只有它能动钱），AI 只负责交叉质询和解释，且必须引用证据编号。

**Q：现在有真实用户吗？**
今天还没有大规模 Agent 争议——但 19 天前 27 家公司刚为这个问题成立联盟，**这个问题的真实性已经不需要我们来证明**。

**Q：C4 判不出来，会不会显得我们没做完？**
恰恰相反。**那是产品最想说的话**，也是 demo 的高潮。做成"全自动判决"才是把项目做废了。
